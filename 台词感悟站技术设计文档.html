0文档说明

0.1 目的

把产品方案与需求翻译成可以直接开工的技术设计：定架构、定渲染方案、定库表、定接口、定部署，并明确与产品文档的偏差及原因。本文档只覆盖一期（P0）；二期内容仅在数据模型和扩展点上预留。

0.2 已拍板的技术决策

  • 1
    数据库：MySQL 8 + mysql2 裸 SQL + 有序校验和迁移复用读书笔记已验证的路由/服务/迁移/备份体系，运维只有一套栈。
  • 2
    登录：用户名 + 密码 + JWT直接复用现有账号体系，零外部依赖；手机号登录作为二期扩展点保留。
  • 3
    渲染：Express 运行时 SSR + 内存缓存登录后页面走 SPA 壳；满足 SEO 硬要求，且不引入 Next.js、不重写前端。
  • 4
    进程：单 Node 进程 + systemd不用 pm2 cluster——限流计数与 SSR 缓存都在进程内存里。
  • 5
    部署：Nginx + Node + MySQL 同机沿用现有 2 核 2G 单机部署，成本最低。
  • 6
    前端：React 18 + Vite 6 + TS，client 与 SSR 双构建与现有客户端代码同构，组件与样式可直接复用。

0.3 与产品文档的三处偏离

需求文档写的是「Express + MongoDB」「手机号验证码」「pm2」，与现有可复用栈不一致。本设计按上表执行：

MongoDB → MySQL 8关系模型清晰，无文档型嵌套需求；迁移校验、mysqldump 备份、事务与 CHECK 约束已在现有项目跑通。产品文档的字段全部保留，落成表结构。
手机号验证码 → 用户名密码短信需服务商、签名报备（1–3 个工作日）与按条计费；现有 JWT + bcrypt + token_version 已满足「感悟归属到人」。预留 phone / login_type 与短信接口位。
pm2 → systemd现有部署手册使用 systemd 单实例，且明确要求单进程；pm2 cluster 会破坏内存限流与 SSR 缓存的一致性。
评审提示：三处偏离需在评审时确认。若坚持 MongoDB 或手机号登录，影响面分别是「全部 SQL 层重写」与「新增短信服务与合规流程」，不在一期范围内。

1.3 三条硬约束

  • 只运行一个 Node 进程。限流计数、幂等缓存、SSR 页面缓存都在进程内存；多实例会让限流与失效逻辑失真。
  • Nginx 与 Node 同机。服务端 trust proxy = loopback，只信任来自 127.0.0.1 的 X-Forwarded-For，用于按真实 IP 限流。
  • 数据库只允许 shiju / shiju_*。启动时校验库名，避免误连读书笔记的 reading_notes 或旧库。

2渲染与 SEO 架构

2.1 为什么是运行时 SSR

方案首屏 HTML内容更新与现有栈复用2C2G 成本
纯 SPA（现状）空壳即时最高最低，但不满足 SEO
构建期预渲染（SSG）完整需重新构建发布，公开感悟有延迟中低
运行时 SSR（选定）完整即时高，仍是一个 Express 进程中，靠缓存摊平
Next.js完整即时低，前端需重写中

公共页每次请求先查内存缓存，命中直接返回字符串；未命中才查询数据库并渲染。内容发布时主动失效，公开感悟与台词的更新没有延迟。

2.2 SSR 执行流程

GET /q/forrest-gump-chocolate
  │
  ├─ 1. 缓存命中且 tag 版本一致、未过期 ──▶ 返回缓存 HTML（ETag / 304）
  │
  └─ 2. 未命中
        ├─ createStaticHandler(routes).query(new Request(内部 URL))
        │     loader 通过 http://127.0.0.1:3001/api/* 取数（不带任何凭证）
        ├─ createStaticRouter(routes, context)
        ├─ renderToString(<StaticRouterProvider router context />)
        ├─ renderMeta(matches, loaderData) 生成 title/description/canonical/JSON-LD
        ├─ 注入 client/dist/index.html 的 <!--app-head--> 与 <!--app-html-->
        ├─ 组装 CSP（内联脚本按内容算 sha256）
        ├─ 写入缓存（HTML + ETag + tags + 过期时间）
        └─ 返回 200
  • 服务端使用 createStaticHandler + createStaticRouter + StaticRouterProvider（react-router 7）；
  • 客户端使用 createBrowserRouter(routes, { hydrationData })，loaderData 由 SSR 注入，首屏不重复请求接口；
  • loader 统一走内部 HTTP 调 /api，不直连 service：序列化逻辑只有一份，service 与 SQL 不会被打进客户端包；loopback 开销 2–4ms，被缓存摊平；
  • 服务端请求不带 Authorization、不读 Cookie，公共页永远是匿名快照——这是缓存安全的前提。

2.6 sitemap 与 robots

GET /sitemap.xml 由 Node 实时拼装，包含：首页、全部 status=1 的台词页、status=1 且至少有一句已发布台词的影片页与主题页；lastmod 取该实体的 updated_at。内存缓存 1 小时 + ETag，内容变更时 bump('sitemap') 失效。500 条台词远低于单文件 5 万条上限；超过 5 万时按 /sitemap-quotes-{n}.xml 分片并生成索引文件。

2.8 hydration 与降级

  • SSR 输出的 HTML 必须与客户端首帧一致：所有随机值（今日一句、时间格式）都在服务端确定并写入 hydrationData；
  • 渲染超时（默认 1500ms）或抛错时，返回 SPA 壳 并带 X-SSR-Fallback: 1 与 Cache-Control: no-store，客户端兜底拉取数据；可用性优先，SEO 降级可观测；
  • 客户端路由切换只对公共页做普通 SPA 导航，不再请求 SSR；回退/前进时浏览器缓存可用；
  • 私有页永远返回 SPA 壳，不参与 SSR。

4数据库设计

4.1 约定

  • 引擎 InnoDB，字符集 utf8mb4，排序规则 utf8mb4_unicode_ci（与现有迁移一致）；
  • 主键 BIGINT UNSIGNED AUTO_INCREMENT（小表可用 INT UNSIGNED）；
  • 时间统一 DATETIME(3)，存 UTC，接口输出 ISO 8601，展示时转 Asia/Shanghai；
  • 字段名 snake_case；状态/枚举用 TINYINT UNSIGNED + CHECK；
  • 感悟按用户意图真删：用户删除执行物理删除（DELETE，点赞随外键级联），管理员只做隐藏（status=2）；台词下架置 status=2，下架且不再恢复置 status=3（墓碑，返回 410）；
  • 外键不级联删除用户内容（RESTRICT），点赞表随感悟级联删除；
  • 迁移文件命名 \d{3}_[a-z0-9_]+\.sql，已执行文件内容不可修改。

4.5 状态与可见性

台词状态机

草稿(0) ──发布──▶ 发布(1) ──下线──▶ 下线(2)
                    ▲                  │
                    └────重新发布──────┘
下线(2) ──永久移除──▶ 墓碑(3)（不可恢复，返回 410）

作品状态：草稿(0) → 发布(1) ↔ 下线(2)。下线作品下的台词即使 status=1 也不可访问。

感悟可见性矩阵

visibility作者好友其他登录用户匿名台词页公开列表读友动态我的本子导出可点赞可评论
0 私密可见不可见（404）不可见（404）不可见不出现不出现出现包含否仅作者
1 好友可见可见（昵称与用户名）不可见（404）不可见不出现出现出现包含是（仅好友）仅作者与读友
2 公开可见可见（昵称与用户名）可见（仅昵称）可见（仅昵称）出现出现出现包含是所有登录用户

评论可见性完全继承所属感悟：能读到感悟的人才能读到并发表评论，读不到感悟的调用者对评论接口一律 404（不是 403，避免枚举）。匿名可读公开感悟的评论，但发表与删除需要登录。

读友动态只展示互为读友者的 visibility IN (1,2) 且 status=1 的感悟；台词页公开列表固定 visibility=2，不因登录状态或好友关系变化，保持 SSR 匿名缓存。

感悟状态：正常(1) / 管理员隐藏(2)。用户删除不做软删除，直接物理删除该行（点赞级联删除）；隐藏仅由管理员触发。隐藏后公开列表、读友动态与导出均不包含；作者可在台词页「我的感悟」、写感悟页和台词本看到只读状态，不能编辑或切换可见范围，只能删除后重写。

4.6 一句一感悟（显式假设）

UNIQUE(user_id, quote_id) 表示「每人在每句台词下只有一条感悟」，编辑即修改该条；删除是真删，之后再写会插入新行（id 变化、like_count 从 0 开始）。
收益：本子按作品分组不出现同一句的多条重复记录；天然限制刷屏；详情页列表以「人」为单位，信息密度稳定。
代价：用户无法对同一句写多篇。此项列入待决项；若改为多篇，只需去掉唯一键并在列表中加入 id 维度，其余接口不变。

4.7 读友与好友可见

  • friend_request 记录双向关系；同一对用户只保留一行，反向申请自动接受。
  • 互为读友后，对方的「好友可见」与「公开」感悟进入 /api/friends/feed；仅好友可对「好友可见」感悟点赞，非好友读取或点赞均返回 404。
  • 台词页公开列表仍只返回公开感悟，不因登录或好友关系变化。
  • 读友列表展示的感悟数只统计对方的好友可见与公开感悟，不含私密与隐藏内容。

4.8 评论

公开感悟之下的一层讨论，一期只做最小闭环：

  • 单层平铺：无回复、无 parent_id、无评论点赞，一条感悟下的评论按时间倒序分页（最新在前，created_at DESC, id DESC）。
  • 入口范围：只在台词页 /q/:slug 的「大家怎么写」公开感悟卡片上展开，读友动态与我的本子不提供评论入口。
  • 长度：300 字（按码点计数，与感悟 500 字同套校验），允许换行，前端 white-space: pre-wrap 渲染，纯文本、无富文本与提及。
  • 权限：能读到感悟即可评论（见 4.5）；删除权限为评论者本人、感悟作者与管理员，删除即物理删除，无编辑、无回收站。
  • 审核：管理员可隐藏（status=2）与恢复单条评论，隐藏只影响公开列表与计数，评论者本人仍可在后台看到。
  • 冻结语义：感悟被管理员隐藏（reflection.status=2）后，其整条评论线程对所有人（含作者）不可读不可写，接口返回 404，仅能由管理员在后台的评论面板处理；感悟本身作者仍可删除，删除时评论随外键级联清空。
  • 计数：感悟卡片的 comment_count 由 reflection_comment 实时 COUNT（只计 status=1），随公开感悟列表一起进入 SSR 缓存。
  • 无通知：一期不做「有人评论了我」的未读提醒，user 表不增加 inbox 字段。

5API 设计

5.1 通用约定

  • 前缀 /api；请求与响应均为 JSON（导出接口除外）；
  • 成功 { "data": ... }；失败 { "error": { "code", "message", "details"? } }；
  • 错误码大写下划线：VALIDATION_ERROR、UNAUTHORIZED、TOKEN_EXPIRED、TOKEN_REVOKED、FORBIDDEN、NOT_FOUND、CONFLICT、RATE_LIMITED、INTERNAL_ERROR；
  • 鉴权 Authorization: Bearer <JWT>；JWT 14 天有效，载荷含 sub（用户 ID）与 tv（token_version）；
  • 分页 page 从 1 开始，page_size 默认 20、最大 50；响应 { items, page, page_size, total, has_more }，与现有 services/notes.js 一致（多取 1 条判断 has_more）；
  • 匿名可读：台词、影片、主题、公开感悟、搜索均无需登录；私密内容与「我的本子」「导出」需要 Token；
  • 幂等：POST /api/reflections、POST /api/reflections/:id/comments、后台发布/导入接受 Idempotency-Key（8–64 位），复用 services/idempotency.js，TTL 10 分钟；
  • 时间 ISO 8601 UTC，如 2026-11-12T04:30:00.000Z；前端统一按 Asia/Shanghai 展示；
  • 请求体限制 1MB；未知字段直接拒绝（复用 readBody）。

6SSR 缓存与失效

6.1 缓存结构

内存 LRU（server/src/ssr/cache.js，手写 Map，不引依赖）：

// 条目
{
  html,                 // 完整 HTML 字符串
  etag,                 // sha1(html)
  tags,                 // ['all','quote:12','work:3','theme:4']
  seen,                 // { 'all': 3, 'quote:12': 7, ... } 写入时的版本快照
  freshUntil,           // 新鲜期结束（毫秒）
  staleUntil            // 可继续返回旧内容的截止时间
}
// 全局
stamps: Map<tag, number>   // 每次失效 +1
  • 上限 400 条，按插入顺序淘汰；单条约 30–80KB，总占用 ≤ 32MB；
  • 键为 path + 规范化 query（如 /q/forrest-gump-chocolate?page=1）；
  • 同一 URL 的并发未命中用 in-flight Map 去重，只渲染一次。

6.2 失效算法：tag 版本戳

export function bump(...tags) {
  for (const t of tags) stamps.set(t, (stamps.get(t) ?? 0) + 1);
}

export function lookup(key) {
  const e = entries.get(key);
  if (!e) return null;
  for (const [tag, version] of Object.entries(e.seen)) {
    if ((stamps.get(tag) ?? 0) !== version) { entries.delete(key); return null; }
  }
  if (Date.now() > e.staleUntil) { entries.delete(key); return null; }
  entries.delete(key); entries.set(key, e); // LRU touch
  return e;
}

为什么不用「URL 列表反查」：一条台词会出现在台词页、影片页、主题页、首页与 sitemap，反查关系复杂且易漏；版本戳让失效变成 O(1)。为什么不映射到单 URL：一个全局计数器会让所有内容变更击穿全站缓存。

6.3 过期策略：SWR

时间窗口行为
now ≤ freshUntil直接返回缓存
freshUntil < now ≤ staleUntil先返回旧 HTML，同时后台重渲染并覆盖（同 key 去重）
now > staleUntil视为未命中，同步渲染

TTL 只是兜底，正确性靠写库后主动 bump。典型 TTL：首页 60s、台词/影片/主题 300s、搜索 120s、sitemap 3600s。

7账号与权限

7.1 账号模型（复用现有实现）

  • 注册：username 3–20 位字母/数字/下划线，密码 ≥ 8 位且 ≤ 64 位（bcrypt 只取前 72 字节），昵称 1–20 字，缺省用用户名；
  • 注册即同意条款：前端勾选框必须勾选，请求体 agree_terms: true 才通过校验，服务端同时写入 user.agreed_at（需求文档的合规要求，避免「默认同意」）；
  • 密码哈希：bcrypt，cost 由 BCRYPT_COST 控制（默认 12）；
  • 登录：失败按账号与 IP 双维度限流；用户不存在时与固定 dummy hash 比对，保持耗时一致，防用户名枚举；
  • JWT：HS256，14 天，载荷 sub + tv；token_version 自增即让该用户所有旧令牌失效；
  • 前端 token 存 localStorage（键 shiju_token），请求失败 401 时清理并提示重新登录；
  • P0 无第三方登录、无个人主页、无自助找回密码；忘记密码由管理员执行 reset-password 脚本（复用现有脚本）。

台词写入时计算两列：

  • search_text：quote_text + speaker + work.title + work.director + theme.name... 经 NFKC 归一、小写、去空白与标点；
  • pinyin：全拼 + 首字母，空格分隔。例如「阿甘正传」→ aganjzhengzhuan agzz。
export function normalize(input) {
  return String(input)
    .normalize('NFKC')
    .toLowerCase()
    .replace(/[\s\p{P}\p{S}]+/gu, '');
}

拼音在导入脚本/后台保存时计算（pinyin-pro 已在客户端依赖中出现，提升为 workspace 根依赖供脚本使用），运行时不做拼音转换，避免每请求 CPU 开销。

8.2 查询

SELECT q.id, q.slug, q.quote_text, q.speaker, w.title
  FROM quote q
  JOIN work w ON w.id = q.work_id
 WHERE q.status = 1 AND w.status = 1
   AND (q.search_text LIKE CONCAT('%', ?, '%') ESCAPE '\\'
        OR q.pinyin   LIKE CONCAT('%', ?, '%') ESCAPE '\\')
 ORDER BY (q.quote_text LIKE CONCAT(?, '%') ESCAPE '\\') DESC,
          q.featured DESC, q.published_at DESC, q.id DESC
 LIMIT ? OFFSET ?;
  • 输入先归一化，并转义 \、%、_，防止通配符注入；
  • 「阿甘」「agz」「forrest」都能命中；
  • 数百到数千行全表扫描 < 5ms，不需要 FULLTEXT；MySQL 的 ngram 解析器需要服务端配置且对 1–2 字中文召回差，一期不引入；
  • 迁移阈值：台词超过 5 万条或搜索 p95 > 150ms 时，改用 FULLTEXT(search_text) WITH PARSER ngram（ngram_token_size=2），并保留 LIKE 作为短词兜底；届时再评估 Meilisearch。

8.3 搜索日志

每次有效搜索（q 非空、长度 ≤ 100）写一条 search_log，失败不阻断响应：

{ "query": "阿甘 巧克力", "normalized": "阿甘巧克力", "result_count": 1, "ip_hash": "…" }
  • ip_hash = sha256(ip + IP_HASH_SALT).slice(0, 32)，不存明文 IP；
  • 零结果报表：
SELECT normalized, COUNT(*) AS times
  FROM search_log
 WHERE result_count = 0 AND created_at >= NOW() - INTERVAL 30 DAY
 GROUP BY normalized
 ORDER BY times DESC
 LIMIT 100;

报表用于补录台词、补充同义词与判断剧集需求；日志保留 180 天后清理。零结果页展示「没找到这句」+「想收录某句台词」入口，登录用户提交后写 quote_request；这是需求文档 F6 的兜底路径，也把「用户想找但站里没有」的信号沉淀到后台（见 10.1）。

10.1 后台页面

后台复用同一 React 应用，路由 /admin/*，仅 role=9 可见，SPA 壳 + noindex：

  • 台词管理：按作品筛选、搜索、编辑、发布/下线、批量录入；
  • 作品管理：新增/编辑影片信息与 slug；
  • 主题管理：排序、描述、上下线；
  • 今日一句：按日期选择台词（不选则走确定性回退）；
  • 感悟管理：按状态查看、隐藏违规内容；行内展开「管理评论」面板，可查看（含已隐藏筛选）、隐藏 / 恢复 / 删除单条评论；

10.2 发布状态机与缓存联动

后台每次发布/下线都走同一个 service，事务内更新状态、维护 work.quote_count、写 slug_redirect（如改 slug）、提交后 bump 对应 tag。不允许直接改库绕过 service。

10.3 种子导入

server/scripts/import-seed.mjs 读取 seed/*.jsonl，默认 dry-run，--apply 才写库。

{"work":{"slug":"forrest-gump","title":"阿甘正传","original_title":"Forrest Gump","year":1994,"director":"罗伯特·泽米吉斯","country":"美国"},
 "quote":{"slug":"forrest-gump-chocolate","text":"生活就像一盒巧克力，你永远不知道下一颗是什么味道。","speaker":"阿甘","context":"阿甘在长椅上对陌生人说起母亲的话","themes":["人生"],"featured":true}}
  • 作品按 slug upsert；台词 source_key = sha1(work.slug + "\n" + text)，重复导入只更新不新增；
  • 主题按 name upsert；
  • 每句校验：1–140 字、必须有出处、context 非空、主题 ≤ 3 个；不通过的行输出到报告并跳过；
  • dry-run 输出：总行数、新增、更新、重复、超长、缺字段；
  • 每次 --apply 写一条 seed_batch（文件 SHA-256 + 统计 + 报告 JSON），同一文件重复执行直接跳过；
  • 导入完成后 bump('all')。

10.4 收录与版权边界

  • 单句节选 ≤ 140 字，必须注明影片、角色与场景；
  • 不使用剧照、海报、截图、配乐；页面视觉依靠排版卡与纯 CSS；
  • 不导入整段剧本、不提供连续对白拼接；
  • 「关于」页提供版权说明与下架通道（/about#takedown），收到通知 48 小时内处理；
  • 上线前做一次合规复核，结论记录在案。

16请求全链路示例

16.1 匿名访问台词页

GET /q/forrest-gump-chocolate
→ Nginx location / → Node :3001
→ SSR cache miss
→ loader: GET http://127.0.0.1:3001/api/quotes/forrest-gump-chocolate
          GET http://127.0.0.1:3001/api/quotes/forrest-gump-chocolate/reflections?page=1
→ MySQL: quote + work + themes；reflection WHERE visibility=2 AND status=1
→ renderToString + meta + JSON-LD
→ cache.put(key, html, ['all','quote:12','work:3','theme:4'])
→ 200 text/html，ETag，Cache-Control: public, max-age=0, must-revalidate

16.2 登录用户写感悟

POST /api/reflections  Authorization: Bearer …  Idempotency-Key: 9f1c…
→ requireAuth（校验 tv）
→ 校验 quote 已发布、body 1–500、visibility ∈ {0,1,2}
→ 事务：INSERT reflection；命中 uk_reflection_user_quote 则回滚并返回 409
→ 提交后 bump('quote:12')（仅当 visibility=2）
→ 201 { data: { id, body, visibility, created_at } }
→ 前端提示「已存入我的本子」

16.3 后台改一句台词

PUT /api/admin/quotes/12
→ requireAuth + requireAdmin
→ 事务更新 quote、重建 search_text/pinyin、写 slug_redirect（若 slug 变化）
→ 提交后 bump('quote:12','work:3','theme:4','home','sitemap') + bump('all')
→ 下一个请求重新渲染并写入缓存
一句话带走：用 MySQL + Express 单进程把公共页做成「匿名 SSR + tag 版本戳缓存」，用「默认私密 + 按作品聚合 + 可导出」把写的人留住，后台与种子导入保证内容底座——整套骨架与读书笔记同源，等于把验证过的工程体系再跑一遍新赛道。
